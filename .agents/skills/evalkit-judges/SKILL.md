# Score EvalKit runs

Read `../evalkit/SKILL.md`, `../../../sites/evalkit.leostera.dev/src/content/docs/manual/scoring-and-evals.md` and `../../../sites/evalkit.leostera.dev/src/content/docs/manual/results.md`, `../../../packages/runner/src/score.ts` (`normalizeScore`), `../../../packages/runner/src/judge-agent.ts` (prompt, retry, recorded fields), `../../../packages/core/src/judge.ts` (`choices`, `criteria`, `judgePrompt`), `../../../examples/starter/judges/greeting.ts`, and `../../../examples/judges/` (choices, criteria and evidence predicates with a matrix-chosen judge model).

EvalKit currently executes deterministic `predicate(name, callback)` scorers and agent-backed `judge(name, { rubric })` rules. A judge rule runs on its own `agent` or the project's `judge` (`defineConfig({ judge })`); it is never the AUT. Give every rule a `description` saying what it checks: the dashboard, `--dry-run` and failure lines show it. The `judgeScorer(...)` API is not implemented—do not suggest it.

1. Add a named `predicate(...)` for deterministic checks or a `judge(...)` descriptor for rubric-based LLM assessment, then reference it from the eval's `scoring` array or supported transcript checkpoint. The predicate callback receives `{ context, output, data, transcript, subagents, runEvents, artifacts, checkpoints, turn? }`; `checkpoints` are earlier checkpoint results (all of them in final scoring), so a checkpoint that inspects live state before the session closes can hand its `evidence` to final scorers. Use `output` for the final assistant reply and `data[id]` for dataset values (expected answers belong in an evaluator dataset); for tool calls or intermediate messages use the helpers `toolCalls(ctx, name?)` (`{ name, arguments, result, isError }`), `messages(ctx, role?)` (`{ role, text }`), `lastReply(ctx)`, `usage(ctx)` and `modelContext(ctx)`; `transcript` is the raw ATXF transcript. `context` includes per-run IDs, metadata, random seed and optional parameters; workspace roots are absolute local paths.
2. A predicate returns a boolean, a finite score from 0 to 1, `{ value, passed?, explanation?, evidence? }` (evidence may be any plain value), or `skip(reason)` when the check does not apply. Without `passed`, only `value === 1` passes; give `predicate(name, fn, { passAt: 0.8 })` for a threshold. A skipped result neither passes nor fails and is left out of averages; never fake "not applicable" as a pass. Use clear evidence for debugging.
3. A `judge(...)` rule: EvalKit builds the prompt from `rubric`, `inputs` (`{ name: (ctx) => value }`, default `conversation` and `reply`) and `answer` (`choices({ A: [label, value] })`, `criteria({ name: weight })`, or the default 0–1 verdict), reads the reply, and asks once more if it cannot. Set `passAt` (default only 1). The judge agent receives `context.parameters`, so a matrix axis such as `judgeModel` can choose its model; it should return `{ reply, usage, model }`. Results save the prompt, reply, conversation, usage, model and `passAt`; judging tokens are the built-in `judge tokens` metric, apart from `tokens`. A predicate may return `criteria` instead of `value`; the score is their weighted mean. Validate that the judge is independent from the AUT, runs in an appropriate workspace, and does not receive secrets. Judge events/prompts may contain sensitive data and incur model cost; cost is not inferred unless the adapter emits usage.
4. Normal scorers are skipped after primary execution errors unless declared with `{ supportsPartial: true }` and the required context/workspace exists. Scorer exceptions and invalid scores become recorded failures; never mask them as passes.
5. Scorers run after the AUT closes; use `node:fs/promises` to inspect candidate/evaluator files before workspace cleanup. Keep evaluator references and secrets out of AUT events, evidence, and exported reports. Reading one evaluator dataset in a trusted adapter and deliberately injecting it as an experiment treatment is valid, but measures injected context—not whether the AUT retrieved it itself.
6. Numbers to compare rather than gate on (tokens, time, retries, mistakes, web searches) are **metrics**, not scorers: `metric(name, (context) => number | undefined, { unit?, better? })` in the eval's `metrics` array. Never fake one as a predicate that always passes. Agent time, tokens (when the adapter reports usage) and tool calls are recorded automatically; have the adapter emit `turn-completed` usage so tokens appear. Means show on the run page and scoreboard.
7. Test passing, failing, and missing-output trajectories; inspect `scoring.json` (`results`, `overall`, `passed`) and run `summary.json`. `overall` is an unweighted mean of valid scores, not the pass rate. A run whose scoring did not pass has `status: 'failed'`; `errored` means it could not finish. For repeats, count the batch's passed runs.

To pass what a checkpoint saw to final scoring, return it as `evidence` and read it with `checkpoint(rule)` (pass the predicate object, not its name): `scoring: [predicate('runs', ({ checkpoint }) => checkpoint(builds)?.evidence?.stdout === 'hi')]`. Never look checkpoints up by name and cast.
